## 1. 项目总览

**一句话**：把任意目录树变成「可校验、可加密、可增量、可淘汰」的快照归档；在此基础上加自动化与网络，扩展成个人网盘。

| 维度 | 内容 |
| --- | --- |
| 技术栈 | Java 21（record、switch 穷尽、HexFormat）、Swing、NIO.2、JCA/JCE、com.sun.net.httpserver |
| 第三方依赖 | 运行期 0，测试期仅 JUnit 5 |
| 代码规模 | 主代码 21 类 + 测试 14 类；102 项自动化测试 |
| 功能覆盖 | 基础 40 分 + 图形界面/打包/压缩×2/加密/定时+淘汰/实时/元数据/文件类型/自定义筛选/网络备份，全部扩展点 |

**模块分包**（接口用 record 冻结，模块间只传值对象）：

```
com.backup
├── core        BackupService / FileScanner / BackupFilter / BackupManifest / BackupCatalog / BackupEntry...
├── io          ArchiveService / FifoSupport / SymbolicLinkPermissions
├── crypto      EncryptionService

├── network     NetworkBackupServer / NetworkBackupClient / NetworkBackupService / NetworkUsers / PasswordHashes
└── ui          BackupFrame（四标签页）
```

## 2. 工作步骤：软件工程全流程复盘

### 2.1 阶段〇：读题与划界（需求分析）

**做法**：先把实验要求逐条翻译成 FR 编号（FR-CORE-01…FR-NET-05），再明确「非作用领域」——多用户权限分级、Windows ACL、在线浏览等**明确不做**。

**为什么重要**：备份软件最容易死在范围膨胀（想做全平台、全格式）。先写"不做什么"，后面每个设计决策都有依据可引。

**产出**：634 行需求说明书 + 2 个关键用例（UC-01 备份 / UC-02 还原，含扩展场景与并发场景）+ 需求-代码追溯表。

### 2.2 阶段一：先设计数据格式，再写代码

这是本项目**最重要的工作方法**：模块可以并行开发的前提是「数据格式先冻结」。

| 冻结的契约 | 内容 |
| --- | --- |
| `BackupEntry`（record） | relativePath / directory / size / lastModifiedMillis / sha256 / permissions / owner / group / type / linkTarget / lastAccessMillis / creationMillis |
| `BackupOptions`（record） | 源/目标/名称/压缩/增量/加密/口令/筛选/保留数 |
| 清单格式 | Properties 文本，version=2，键值前缀 `entry.N.` |
| 快照索引格式 | version=1，taskId/snapshotId/groupId/parentId/sequence/archiveName/createdAt |

record 的好处：不可变、天然 equals/hashCode、构造器即校验点（compact constructor 里做参数规范化，坏数据进不了系统）。

### 2.3 阶段二：编码顺序（依赖驱动，而非功能驱动）

```
第 1 步 FileScanner（能把树读成 List<BackupEntry>）
第 2 步 BackupManifest（能把 List 写成/读回文本）
第 3 步 ArchiveService ZIP 写/读（round-trip 打通：备份→还原→内容一致）
第 4 步 BackupService（编排 + 事务发布）
第 5 步 增量判定 + 组轮换
第 6 步 EncryptionService（整体加密，最后挂上）
第 7 步 GZIP 容器 + 元数据还原 + 特殊文件
第 8 步 Swing UI + 自动化
第 9 步 网络包（复用前八步的全部能力）
```

**原则**：每一步结束都有一个「round-trip 通过」的可运行状态。绝不先写 UI 再补核心。

### 2.4 阶段三：测试先行 + 平台假设

每个功能同时落两条测试：**正路径**（round-trip 相等）+ **对抗路径**（截断、篡改、穿越、并发）。平台相关用例用 `assumeTrue(能力可用)` 守卫——支持的平台实跑，不支持的跳过并如实记录，不假装全平台通过（`testing/FileSystemCapabilities` 统一探测 POSIX 视图、链接创建能力、文件身份）。

### 2.5 阶段四：Git 工作流

- 功能分支（`codex/...`）+ `--no-ff` 合并，提交图保留开发线
- **每次提交前**把暂存区导出到独立目录跑测试，保证任何提交单独 checkout 都是绿的
- 文档与代码同步提交，需求-代码追溯表随代码演进

## 3. 板块一：目录扫描与文件分类（FileScanner）

### 问题
把一棵任意的目录树读成 `List<BackupEntry>`，要求：不跟随符号链接、识别特殊文件、同一硬链接只存一份内容、顺序确定。

### 算法：两遍扫描

**第一遍（walkFileTree）**：`SimpleFileVisitor` 收集 `RawEntry`（路径 + 属性 + 属主 + 分类结果）到 `TreeMap<String, RawEntry>`——TreeMap 保证相对路径字典序，输出确定性（对测试和增量比较都关键）。

**分类算法**（visitFile 内）：

```java
EntryType type = attrs.isDirectory()  ? DIRECTORY
               : attrs.isSymbolicLink() ? SYMBOLIC_LINK
               : attrs.isRegularFile()  ? FILE
               : classifySpecial(path, attrs);   // 兜底：unix 类型位
```

`classifySpecial` 用 `Files.getAttribute(path, "unix:mode")` 取原始 st_mode，按类型位掩码判类：

| 位运算（mode & 0170000） | 类型 |
| --- | --- |
| 0010000（八进制） | FIFO 管道 |
| 0020000 | 字符设备 |
| 0060000 | 块设备 |
| 0140000 | Unix 域套接字 |

> 为什么不用公开 API？因为 JDK 没有公开的文件类型位 API，`unix:` 视图是 OpenJDK 在 Unix 平台的扩展；Windows 上抛 `UnsupportedOperationException` → 返回 null → 跳过并警告。这是「能力探测 + 降级」模式。

**属主采集**：先试 `PosixFileAttributes`（Unix），`UnsupportedOperationException` 时退到 `FileOwnerAttributeView`（Windows，取到 `机器名\用户` 形式）。属主同时用于筛选条件和清单记录。

**第二遍（构建 BackupEntry）**：

1. **父目录保留算法**：任何非目录条目被选中后，把其所有祖先路径加入 `needed` 集合——目录只有「被明确排除」或「不在 needed 且筛选非空」时才剪掉。这保证还原时父目录一定存在，又不带入无关空目录。
2. **硬链接识别算法**：

```java
BackupEntry first = byIdentity.get(attrs.fileKey());   // fileKey = 文件系统级身份
if (first != null) { type = HARD_LINK; target = first.relativePath(); hash = first.sha256(); }
else { hash = sha256(path); byIdentity.put(fileKey, entry); }
```

同一 `fileKey` 第二次出现时不再读文件算哈希，只记录「指向第一个名字」——**同一内容只读一次磁盘**，且天然保持链接关系。Windows 的 `fileKey()` 返回 null → 每个名字都当普通文件存并输出警告（降级）。

3. **设备号解码**：`unix:rdev` 取原始 st_rdev，按平台位布局拆 major/minor（Linux 用 glibc 大编码宏，macOS 用 BSD 高 8 位/低 24 位），存成 `"major:minor"` 字符串进清单的 linkTarget 字段。

### 验证
中文/空格路径、空目录、FIFO/设备/套接字分类、断链不阻塞扫描、硬链接组只算一次哈希——均有专项测试。

## 4. 板块二：清单 Manifest——快照的"身份证"

### 问题
归档文件本身不说明自己是谁。必须有一个自描述、可校验、向前兼容的元数据格式。

### 思路
选 **Properties 文本**而非 JSON/XML：JDK 原生、转义规则成熟（unicode/换行/反斜杠）、diff 友好、手写解析零依赖。

### 格式（version=2）

```properties
version=2
sourceRoot=/path/to/source
createdAt=2026-11-05T12:00:00Z
compressionType=ZIP
incremental=true
encrypted=false
entry.count=3
entry.0.path=docs/readme.txt
entry.0.directory=false
entry.0.size=1024
entry.0.lastModifiedMillis=1600000000000
entry.0.sha256=ab12...
entry.0.permissions=rw-r--r--
entry.0.owner=alice
entry.0.group=staff
entry.0.type=FILE
entry.0.linkTarget=
entry.0.lastAccessMillis=...
entry.0.creationMillis=...
```

**版本兼容设计**：读入时 `version ∈ {1,2}` 均接受；v1 缺失字段全部给默认值（type 缺省按 directory 推导、时间缺省 null 表示"不发明"）。这样旧版本归档永远可还原，新字段只增不破。

**加载防御**：entry.count 上限 100 万（防恶意清单内存爆炸）；非法数字/枚举名统一包成 `IOException("Invalid backup manifest")` 而不是让 NumberFormatException 冒出去。

**写入原子性**：临时文件 + `ATOMIC_MOVE`——任何时刻磁盘上的清单要么是旧的完整的，要么是新的完整的，绝无半份。

## 5. 板块三：归档格式与打包算法（ArchiveService）

### 5.1 ZIP 布局

```
BACKPACK-MANIFEST.properties   ← 第一个条目固定是清单（还原时先读它才能校验后续条目）
data/docs/readme.txt           ← 全部真实条目加 data/ 前缀
data/图片/照片.png
```

- `data/` 前缀把「元数据」和「用户数据」在名字空间上隔离，还原时遇到非 `data/` 前缀直接报错（防伪造条目）
- 每个条目 `setLastModifiedTime`（ZIP 自带时间戳，冗余一层保险）

### 5.2 GZIP 自定义容器（二进制流）

GZIP 只能压缩单流，所以自定容器格式（大端）：

```
[string "BACKPACK-GZIP-2"]      魔数（4字节长度 + UTF-8）——识别 + 版本
[int manifestLength]            清单长度（1B~64MB 边界校验）
[manifest bytes]
[int entryCount]
对每个条目：
  [string path] [boolean directory] [long size] [long lastModifiedMillis]
  [size bytes payload]           仅 FILE 有；FIFO/设备/目录为 0 字节
```

**为什么不用 ZIP 就好？** 多一种算法是实验给分点；同时 GZIP 路径是**完全自控的二进制协议**——长度字段全部有界校验（负数/超大直接 EOFException），是练习「不可信输入解析」的好载体。

### 5.3 打包中的一致性校验（关键算法）

写每个 FILE 条目时不是简单复制，而是**边拷边算哈希**：

```java
MessageDigest digest = SHA-256;
try (InputStream in = new DigestInputStream(Files.newInputStream(path), digest)) {
    long written = in.transferTo(out);
    if (written != entry.size() || !HexFormat.of().formatHex(digest.digest()).equals(entry.sha256()))
        throw new IOException("Source changed while backing up: " + path);
}
```

**为什么**：扫描（算哈希）和打包（写内容）之间有时间窗，源文件可能被修改。若只看尺寸，同尺寸篡改会产出**永远无法通过还原校验的归档**。这里宁可备份失败也不发布坏归档——「拒绝发布不一致归档」有专项回归测试。

## 6. 板块四：增量备份判定算法

### 问题
第二次备份怎么只打包"变化的东西"，且保证还原结果与全量一致？

### 思路：清单记全量，归档存增量

每次备份的清单都记录**当前完整快照**（所有条目）；归档载荷只放「与基线不同」的条目。这样增量归档自带完整语义（清单可独立校验），还原时按序叠加即可。

### 判定算法

```java
boolean incremental = options.incremental() && baseline != null
                      && baseline.compatible(options)          // 压缩/加密/口令/保留开关一致
                      && baseline.manifest().snapshot().sequence() < 10   // 组未满
                      && baseline.chainAvailable();            // 基线链文件齐全
archived = scanned.filter(e -> e.directory() || !e.sameContentAs(previous.get(e.relativePath())));
```

`sameContentAs` 的比较集：**type、size、lastModifiedMillis、sha256、linkTarget、permissions、owner、group**。八个字段全等才算"没变"——任何一项变（哪怕只是 chmod）都会进入增量。目录条目恒随附（还原时需要 mkdir 语义）。

### 基线的生命周期

- 基线 = `(manifest, 压缩类型, 加密标志, 口令副本, 保留开关, 链文件列表)`，存于 `Map<目标目录+taskId, Baseline>`
- **任务身份 taskId** = SHA-256(`len:源真实路径` + `len:备份名` + `len:筛选identity`)——长度前缀拼接防歧义（"ab"+"c" vs "a"+"bc"）
- 换任务/换进程/改压缩/改加密/改口令/开关联保留 → 基线不兼容 → 自动退化为全量。**宁全量不猜链**，是增量安全的第一原则

### 增量还原的基线核验算法（最容易做错的点）

增量归档只含部分条目。还原时，**没出现在归档里的清单条目**不能盲目套属性，必须先核验已还原的基线内容：

```java
if (baselineMatches(root, entry)) metadata.add(entry);      // 内容一致 → 回填时间/权限
else warnings.add("...baseline missing or different; restore the full backup first");
```

`baselineMatches` 对 FILE 比较尺寸+SHA-256、对 HARD_LINK 额外要求 `isSameFile`、对 FIFO 比较类型位、对符号链接比较目标串。**防止把 A 快照的属性写到 B 的内容上**——缺失或不匹配只警告，绝不改数据。

## 7. 板块五：组轮换与数据淘汰（BackupCatalog）

### 问题
保留 N 份备份时，怎么删才不会删断增量链？目录里有别人的文件、损坏的清单怎么办？

### 思路：所有权显式化 + 保守删除

**所有权显式化**：每个归档旁有 `.snapshot.properties` 索引（version=1）：

```properties
taskId=…（哪个任务）  snapshotId=…（本次唯一 ID）
groupId=…（属于哪组）  parentId=…（上一快照 ID，全量为空）
sequence=3            archiveName=demo-full-20261105-….zip
createdAt=2026-11-05T…
```

**组语义**：sequence 1..10；sequence=1 时必须 `snapshotId == groupId` 且无父；之后每个 parentId 必须等于前一快照的 snapshotId（`validateChain` 校验连续且无分叉）。第 11 次备份即使 keepGroups=0 也强制开新组——链长度有上限，防无限膨胀。

### prune 算法（逐步）

```
1. 扫描目录所有 *.snapshot.properties，逐个解析；
   任何解析失败 → 标记 corrupt，警告，【整体放弃本轮清理】
   （不可信记录可能属于任何组，猜错就丢数据）
2. 按 taskId 过滤出本任务的快照，按 groupId 分组
3. 每组排序后 validateChain：根必须 sequence=1，链必须连续无分叉；
   再 verifyPair：归档+清单旁挂文件存在、清单版本=2、六个身份字段与索引一致
4. 有效组按"全量根的 createdAt"倒序排列
5. 从第 keepGroups+1 个组开始删除：
   - 若该组包含全目录最新快照 → 跳过（保护最新）
   - 每删一条前重读索引确认身份未变（防 TOCTOU）
   - 删 归档 → 清单旁挂 → 索引；任何一步失败 → 停止本组，保留剩余祖先链
6. 不同任务的组、无关文件、未知文件：永远不碰
```

**设计哲学**：宁可少删（保留量暂时超过 N），不可错删。清理失败只作为备份结果的警告，不影响本次备份的成功性。

## 8. 板块六：加密解密（EncryptionService）

### 需求
用户给口令 → 整个归档加密；口令错误必须**干净地失败**（不能产出坏数据）。

### 算法选型

| 组件 | 选择 | 理由 |
| --- | --- | --- |
| 加密 | AES-256-**GCM** | 认证加密：机密性 + 完整性一步到位，篡改任一比特解密即失败 |
| 密钥派生 | PBKDF2-HmacSHA256，**210000 次迭代**，16 字节随机盐，256 位输出 | 慢哈希把"每秒十亿次穷举"压到"每秒几千次"，盐防彩虹表 |
| IV | 12 字节随机（每次加密新生成） | GCM 对 IV 重用极度敏感，绝不复用 |
| 认证标签 | 128 位 | NIST 推荐上限 |

### 文件格式

```
"BPACKENC1"          9 字节魔数（isEncrypted 只读这 9 字节即可判断）
[int 16][salt]       长度前缀 + 盐
[int 12][iv]         长度前缀 + IV
[GCM 加密流]         CipherOutputStream（tag 自动附加在尾部）
```

### 流程

```
加密：明文归档写临时文件 → 读头(魔数/盐/IV) → Cipher(DECRYPT…) 
      （还原）GCM 流式解密到目标临时文件 → 原子替换；finally 删除明文临时文件
```

### 踩坑与修复（重要！）

JDK 的 `CipherInputStream` 在流末尾做 GCM tag 校验，**失败时抛的是普通 IOException**（消息 "Tag mismatch"），不会被 `catch (GeneralSecurityException)` 捕获——用户看到的错误是密码学堆栈原文。修复：

```java
} catch (IOException streamFailure) {
    if (streamFailure.getCause() instanceof GeneralSecurityException
            || streamFailure.getMessage() != null && streamFailure.getMessage().contains("Tag mismatch")) {
        throw new IOException("Unable to decrypt backup. Check the passphrase.", streamFailure);
    }
    throw streamFailure;
}
```

**教训**：包装类（CipherInputStream/CipherOutputStream）会改变异常类型，安全边界代码必须显式测试"错误输入"路径（我们有：错误口令还原 → 失败且目标目录无内容）。

## 9. 板块七：还原流程与安全防御

### 流程

```
识别格式（PK→ZIP / 1F 8B→GZIP） → [加密则解密到临时文件] 
→ 读清单 → validateManifest（结构校验） → 逐条目 restorePayload（写数据）
→ finish()：重建链接（硬/软） → 增量基线核验 → 按目录深度从深到浅回填元数据
```

### 四层安全算法

**① 路径穿越防御（safeResolve）**——每一层都过：

```java
拒绝：空路径 / 含反斜杠 / 绝对路径 / 任何 "." ".." 组件
Path resolved = root.resolve(path).normalize();
拒绝：resolved == root || !resolved.startsWith(root)   // 规范化后逃逸检测
```

测试用例：手工构造 `entry.0.path=../outside` 的恶意归档 → 还原抛异常且外部哨兵文件内容不变。

**② 符号链接防御（checkParents）**——从 root 到目标逐级检查 `isSymbolicLink`：恶意归档可以包含 `link → /etc` + `link/passwd` 两步组合，逐级检查让第二步必然失败。同时**拒绝覆盖已存在的符号链接**（防止借还原把内容写到链接目标）。

**③ 原子替换保护外部硬链接**——写常规文件不是 in-place 截断，而是：

```
写同目录临时文件 → 校验 SHA-256 → ATOMIC_MOVE 替换目标
```

若目标是目录外某文件的硬链接，in-place 截断会**改掉外部文件内容**；临时文件+替换则让旧 inode 原样保留。有专项测试（restore 后外部哨兵文件内容不变）。

**④ 两阶段链接重建**——payload 阶段跳过链接条目（它们没有数据），全部数据写完后在 `finish()` 统一重建：硬链接先校验基文件存在且 SHA-256 一致再 `Files.createLink`，失败直接抛错（宁可失败也不产出静默错误的还原结果）。

### 元数据回填顺序

按路径深度**从深到浅**排序后回填——先把子目录/文件的时间权限设好，最后设父目录；否则先锁父目录权限（如 r-x）会导致子项写不进去。属主/组查找失败（用户不存在）只产生路径级警告，数据已安全落地。

## 10. 板块八：特殊文件处理

### 设计不变量（FIFO 的生命线）

> **从备份到还原，任何代码路径都不打开管道的数据流。**

打开 FIFO 的读端会阻塞到有写者出现——备份/还原若误读管道，进程就永久挂死。具体落实：

- 扫描：只用属性（`unix:mode`），不 open
- 归档：FIFO 是零载荷条目，不读内容
- 还原：`mkfifo -m <八进制权限>` 在暂存路径创建 → 用 `isFifo()`（属性检查）验证真的建出来了（防 mkfifo 假成功）→ 原子移动到位
- 元数据：时间用 `touch -c -h`（带超时、不跟随）等外部工具而非可能触发 open 的 JDK 调用；权限已在 mkfifo 时烘进去，不一致时重建

### 三类特殊文件的策略矩阵

| 类型 | 扫描 | 清单 | 还原 | 失败行为 |
| --- | --- | --- | --- | --- |
| FIFO | `unix:mode` 类型位 | 零载荷、无目标 | mkfifo（POSIX） | 警告 + skipped + 保留已存在目标 |
| 字符/块设备 | 同上 + `unix:rdev`→"主:次" | 零载荷 + 设备号白名单 `[0-9]{1,5}:[0-9]{1,5}` | mknod（通常需 root） | 同上 |
| 套接字 | 同上 | 零载荷、无目标 | **不重建**（没有监听进程的 socket 文件无意义） | 记录性警告 |
| 软链接 | NOFOLLOW | 目标串 + 自身时间/属主 | `createSymbolicLink`；macOS 用 `chmod -h`(lchmod) 恢复自身权限 | 平台不支持 → 警告 |
| 硬链接 | fileKey 分组 | 目标 = 首名字 | 校验基文件哈希后 createLink | 基文件缺失 → 明确失败 |

**skipped 语义**：特殊文件创建失败时进 `skipped` 集合——它们不算"还原失败"（数据本身就没有），但也不参与后续元数据回填，且全量归档完整性检查把它们计入清单条目（还原结果 = 清单全覆盖 + 警告说明）。

### Windows 降级矩阵（如实写入文档）

| 能力 | Windows 现状 | 原因 |
| --- | --- | --- |
| 硬链接识别 | 降级为普通文件 + 警告 | `fileKey()` 返回 null（公开 API 无文件身份） |
| FIFO/设备/socket 识别 | 跳过 + 警告 | `unix:` 视图不可用 |
| 软链接创建/还原 | 支持 | `Files.createSymbolicLink` 可用（管理员或开发者模式） |
| POSIX 权限/组 | 恢复时警告跳过 | 无 POSIX 视图 |

## 11. 板块九：自动化

### 11.1 定时备份（ScheduledBackupRunner）

- `Executors.newSingleThreadScheduledExecutor`，守护线程命名 `backup-scheduled-backup`
- `scheduleAtFixedRate`（固定频率，不是固定间隔——积压时追平而非顺延）
- `start()` 内先 `stop()`：重复启动 = 重新配置周期，不会出现双调度
- 取消用 `cancel(false)`：让正在写归档的任务跑完（中断写一半的归档 = 损坏文件）

### 11.2 实时备份（WatchBackupService）

三个算法点：

1. **递归注册**：WatchService 不递归 → 启动时 walkFileTree 给每个子目录注册 WatchKey，`Map<WatchKey, Path>` 反查目录
2. **动态注册**：ENTRY_CREATE 且是新目录 → 立即递归注册，否则新目录里的变化全丢
3. **防抖**：编辑器一次保存 = 多个事件（临时文件+重命名）。算法：

```
事件到达 → dirty=true, lastChange=now
轮询循环（poll 500ms，不用 take() 阻塞——让 stop() 最多 500ms 生效）：
  if dirty && now-lastChange ≥ debounce(下限250ms) → dirty=false; 触发备份
```

4. **会话隔离**：重启 watch 时旧循环通过 `watchService == session` 判断自然退出——旧会话的死循环绝不能杀掉新会话

### 11.3 任务闸门（BackupTaskGate）——忙时合并不丢失

**问题**：实时/定时触发时上一次备份还没跑完怎么办？丢掉？排队？重试？

**算法**：每个自动化任务 key 只保留**最新一个** pending starter（LinkedHashMap，先到先序）：

```
submit(key, starter):  busy? → pending[key]=starter（覆盖旧的）
                       else → busy=true; dispatch(starter)
complete():            pending 有货 → dispatch(下一个)（busy 保持 true）
                       else → busy=false
cancel(key):           pending.remove(key)   （停止任务时取消其待执行请求）
```

dispatch 里的 `started` 标志处理了一个微妙竞态：executor 拒绝时不能既抛异常又让 complete 流转，避免双 complete。手动请求在 busy 时直接拒绝（弹窗提示），自动请求合并——**丢失的是过期的中间状态，保留的是最新意图**。

## 12. 板块十：网络备份

### 12.1 总体判断：不发明新协议，复用本地模型

| 网络子问题 | 解法 | 复用 |
| --- | --- | --- |
| 传输加密 | HTTPS（JDK HttpsServer/HttpClient），首次启动 keytool 自动生成自签名证书（PKCS12，SAN 含 localhost/127.0.0.1） | JDK |
| 身份认证 | HTTP Basic（凭据在 TLS 信道内） | JDK |
| 账号存储 | `users.properties`：每账号盐值(16B)+PBKDF2 验证值(210000 迭代)+迭代数；**明文口令永不落盘** | 复用加密模块思路 |
| 存储布局 | 用户名白名单 `[A-Za-z0-9][A-Za-z0-9._-]{0,31}` → `users/<账号>/` 目录，内部与本地目标目录**完全同构** | 目录即协议 |
| 元数据管理 | 清单旁挂 + 快照索引即元数据；`/api/snapshots`、`/api/manifest` 下发 | BackupCatalog |
| 保留淘汰 | 服务器收到 commit 后调 `BackupCatalog.prune` | 直接复用 |
| 增量 | 客户端拉服务器清单当基线，判定逻辑与本地一致 | BackupService.taskIdentity + FileScanner |

### 12.2 协议设计（为什么是 Properties 而不是 JSON）

- 所有请求/响应体（除归档字节流）用 **Properties 文本**：JDK 原生读写、转义成熟、清单本身就是 Properties（一次序列化直接内嵌），省掉手写 JSON 解析器的注入风险
- 请求体上限 64MB 校验；所有名字参数过 `[A-Za-z0-9][A-Za-z0-9._-]{0,199}` 白名单（归档名、查询参数），目录穿越在用户名和文件名两层都被结构上排除

### 12.3 两段式上传（解决"大文件 + 元数据一致性"）

```
POST /api/upload          归档字节流 → users/<u>/.incoming-<uuid>.part → 返回 token（内存表，1 小时过期）
POST /api/commit          Properties{token, keepGroups, manifest(全文)}
                          → 解析清单 → 校验快照身份与归档名
                          → ATOMIC_MOVE 暂存文件为最终归档
                          → 写清单旁挂 → BackupCatalog.publish（校验成对存在+身份一致）
                          → 写最新清单 → prune(keepGroups)
                          → 任一步失败：删除本次已发布产物（回滚），暂存文件清理
```

**为什么两段**：归档几百 MB 而 commit 消息只有几 KB——流式收大文件与原子提交元数据解耦；token 绑定暂存文件路径（校验 parent 目录属于该用户），杜绝跨用户/跨路径写入。启动时清扫残留 `.incoming-*.part`。

### 12.4 网络增量算法

```
taskId = BackupService.taskIdentity(源, options)        // 与本地同一算法
remote = listSnapshots() 过滤 taskId → 取 sequence 最大者
baseline = fetchManifest(remote.archiveName)            // 服务器清单当基线
incremental ⇔ options.incremental && baseline 存在
             && baseline.compressionType == options.compressionType
             && baseline.encrypted == options.encrypted
             && (未加密 || 口令与进程内记忆一致)
             && remote.sequence < 10
新快照：sequence = remote.sequence+1，parentId = remote.snapshotId，groupId 继承
        （任一条件不满足 → 全量：groupId = 新 snapshotId，sequence = 1）
```

**口令记忆**：加密链的口令一致性由客户端进程内 Map 保证（与本地 BackupService 同模型）——换进程自动全量，宁可重传不可断链。

### 12.5 客户端 TLS 信任固定

自签名证书没有 CA 链。方案：客户端**显式信任服务器密钥库文件**（TrustManagerFactory 直接加载 `server-keystore.p12`）——信任根从"权威机构"换成"你亲手拷贝的这个文件"，适合局域网点对点。同时放宽主机名校验（信任已由文件钉死），让 localhost 和局域网 IP 都能用。

### 12.6 还原 = 下载 + 原封不动的本地还原

`NetworkBackupService.restore` 只做一件事：下载归档到临时目录 → 调 `BackupService.restoreDetailed`。**路径安全、符号链接防御、元数据回填、增量基线核验全部零改动复用**——网络层永远不会比本地层更不安全。

## 13. 板块十一：筛选条件引擎（BackupFilter）

### 语义（先定义死，再实现）

| 规则 | 内容 |
| --- | --- |
| 同类 OR | 分号分隔的同类值任一命中即可 |
| 异类 AND | 路径、名字、属主、扩展名、时间、尺寸全部同时满足 |
| 排除优先 | excludePaths 命中即出局，其它条件不再看 |
| 路径 | 源相对路径、`/` 分隔、glob（`**/` 可匹配零层目录） |
| 名字 | 只匹配 basename |
| 属主 | 精确匹配、忽略大小写；**记录为空的属主不命中任何非空条件**（防止"没采到属主"被误当成"任意属主"） |
| 扩展名 | 忽略大小写与前导点；`无扩展名`复选框：无扩展名列表时=只选无扩展名文件，有列表时=追加无扩展名 |
| 边界 | 时间/字节数上下界均包含端点 |

### 实现要点

1. **规范化即校验**：compact constructor 里 strip → 去重 → 排序 → 小写（扩展名/属主），相同的语义必然得到相同的字符串——这是后面「相同筛选 = 相同任务身份」的基础。同时在这里预编译 glob（非法模式立刻抛异常，**在扫描前**失败）
2. **glob 编译**：借 `FileSystems.getPathMatcher` 验证语法合法性，再手写转译成正则（`**/` → `(?:.*/)?`，`{a,b}` → `(?:a|b)`，字符类转义）
3. **性能**：编译结果放 LRU 缓存（256 容量，synchronized LinkedHashMap accessOrder）——大目录扫描时不重复编译
4. **identity()**：`filter-v2:` + 所有字段长度前缀拼接——任何字段变化都改变任务身份（旧链自动失效开新组），这是增量安全的一部分

## 14. 难点复盘：十个坑与解法

| # | 现象 | 根因 | 解法 | 教训 |
| --- | --- | --- | --- | --- |
| 1 | Windows 测试 5 项失败 | `fileKey()` 返回 null，硬链接识别失效 | 能力假设 `assumeTrue`；降级为普通文件+警告 | 跨平台先探测能力，别信"应该有" |
| 2 | 错误口令报错是密码学堆栈原文 | CipherInputStream 把 GCM 失败吞成普通 IOException | 识别 Tag mismatch 转友好提示 | 包装类改变异常类型，安全路径必须专项测试 |
| 3 | FIFO 还原可能永久阻塞 | 打开管道读端会等待写者 | **不打开流**不变量：mkfifo 建节点、属性验证、touch 设时间 | 特殊文件的 I/O 语义要先于功能设计 |
| 4 | macOS 软链接权限改不到链接自身 | JDK setter 可能跟随目标 | BSD `chmod -h`（lchmod）+ 5 秒超时 + 结果校验 | 平台缺口用平台原生工具补，但要有超时与降级 |
| 5 | 淘汰可能删断链 | 按个数删除不感知链依赖 | 组为单位 + 索引验链 + 保守放弃 | 删除策略的默认值应该是"不删" |
| 6 | 忙时自动触发丢失/重复 | 并发完成时序 | TaskGate：按任务 key 合并 pending + started 标志防双 complete | 并发原语要写状态机注释并单测竞态 |
| 7 | 增量还原把属性写错对象 | 基线缺失时盲目回填 | baselineMatches 内容核验，不符只警告 | 元数据回填前必须验内容归属 |
| 8 | 同尺寸篡改产出坏归档 | 扫描与打包间的时间窗 | DigestInputStream 边拷边验，不一致拒绝发布 | 备份的失败好过静默损坏 |
| 9 | 自签名证书信任问题 | 无 CA 链 | 信任固定到服务器密钥库文件 | 局域网点对点场景信任根可以是"文件" |
| 10 | 恶意归档穿越/伪造条目 | 归档是不可信输入 | data/ 前缀隔离 + safeResolve + 逐级符号链接检查 + 长度边界 | 把每个归档都当攻击者输入对待 |

## 16. 学习收获清单

### 设计模式与原则
- **record 值对象**：不可变数据 + 构造即校验，模块间契约清晰
- **能力探测 + 降级**：跨平台代码的正确姿势（探测 → 全力 → 失败降级为警告，绝不假装成功）
- **事务式发布**：临时文件 + ATOMIC_MOVE + finally 清理 + 回滚，保证任何时刻磁盘状态合法
- **保守删除**：涉及不可逆操作（淘汰）时，验证不过就放弃
- **复用而非重写**：网络服务器直接复用本地目录布局与 BackupCatalog，客户端还原直接调本地服务——网络层只做"搬运"

### JDK 能力清单（本项目实际用到）
`Files.walkFileTree / NOFOLLOW_LINKS / ATOMIC_MOVE`、`WatchService`、`unix:mode/rdev` 属性、`fileKey`、`Files.createLink/createSymbolicLink`、`DigestInputStream`、`AES/GCM/NoPadding`、`PBKDF2WithHmacSHA256`、`HttpsServer/HttpClient`、`keytool` 进程调用、`ProcessBuilder`（mkfifo/mknod/chmod/touch 带超时）

### 值得写进报告的一句话总结
> 本项目最大的工程决策是：**把"备份什么"和"怎么存"解耦成清单协议，把"本地"和"网络"解耦成同一个存储模型的两种入口**——前者让增量/淘汰/加密/筛选成为正交功能，后者让网盘模式只花了约 1400 行就完整落地。
