### 2.3 功能、算法、库和实现位置

正文第 2 页只放精简分组，以下细节主要用于讲稿、备查页与回答追问。

| 功能 | 实际实现方式 | 第三方库情况 | 主要源码 |
| --- | --- | --- | --- |
| 目录备份 | `Files.walkFileTree` 递归遍历；清单记录路径与元数据 | JDK NIO | `core/FileScanner.java`、`core/BackupManifest.java` |
| 五类筛选 | 路径与名称 glob；扩展名；修改时间；字节尺寸；同类多值 OR、不同条件 AND、排除优先 | 自己实现规则组合，使用 JDK 模式匹配能力 | `core/BackupFilter.java` |
| 软链接 | 保存链接目标字符串，不跟随链接读取目标；还原时重建 | JDK NIO | `core/FileScanner.java`、`io/ArchiveService.java` |
| 硬链接 | 按文件系统身份识别，共用一个有效载荷，还原时重建硬链接 | JDK NIO；不是按哈希相等认定硬链接 | 同上 |
| 元数据 | 采集修改、访问、创建时间及 POSIX 权限、属主、组；内容恢复后回填，目录从深到浅处理 | JDK 属性视图 | 同上 |
| 打包、压缩 | ZIP；自定义多条目容器加 GZIP，清单内嵌 | JDK `java.util.zip`；不声称自研压缩算法，也不称为 tar.gz | `io/ArchiveService.java` |
| 密码加密 | AES-256-GCM；PBKDF2-HMAC-SHA256 派生密钥；随机盐及 IV | JDK JCA/JCE；不声称自研密码算法 | `crypto/EncryptionService.java` |
| 增量备份 | SHA-256 内容摘要，结合类型、修改时间、权限、属主/组、链接目标判断条目变化；清单仍记录整个当前快照 | JDK 摘要算法 + 自定义清单逻辑 | `core/BackupService.java`、`core/BackupEntry.java` |
| 整组淘汰 | 一组全量加最多九份增量；新归档成功发布后才清理旧组，保护依赖与其他任务 | 自己实现组索引与保留规则 | `core/BackupCatalog.java` |
| 定时备份 | 固定间隔调度，配置在启动时捕获 | JDK `ScheduledExecutorService` | `automation/ScheduledBackupRunner.java` |
| 实时备份 | 递归 `WatchService`，变化防抖、新目录注册；忙时按任务合并后续请求 | JDK `WatchService` + 自己实现任务门控 | `automation/WatchBackupService.java`、`BackupTaskGate.java` |
| 图形界面 | SwingWorker 执行耗时操作，EDT 更新界面；备份/还原互斥 | JDK Swing | `ui/BackupFrame.java` |

加密参数仅建议放备查页：PBKDF2 210,000 次、盐 16 字节、IV 12 字节、GCM 标签 128 位。参数不等于已经进行过密码学审计。

### 2.4 必须准确说明的边界

- 不支持网络备份；不支持管道、设备和 socket 特殊文件，遇到会提示跳过。
- 增量恢复需先全量、再逐份叠加增量；不自动寻找整条链，不同步删除源端已删除的文件。
- 新进程的首次备份为全量；切换任务、压缩、加密或有效密码等配置也可能创建新全量。
- 每组最多 10 次快照，第 11 次新建全量组。保留值 0 表示不删除，正数表示保留最近 N **组**，不是 N 个归档。
- 属主、组及创建时间受权限和文件系统支持限制，失败产生警告。
- 为避免 macOS API 经软链接修改外部目标，软链接属主、组、权限不回填并提示；时间仍通过不跟随方式尝试恢复。
- 绝对软链接还原后仍指向原来的绝对路径；相对软链接会相对于还原目录解析，不能把二者说成相同效果。
- 当前仅 macOS 实机验证，不能写“所有操作系统实测通过”。

### 4.1 数据与环境提前准备

核对命令例子（先确认环境变量仍为本次临时目录）：

```bash
diff "$PPT_DEMO_ROOT/source/docs/report.txt" "$PPT_DEMO_ROOT/restored-full/docs/report.txt"
ls -li "$PPT_DEMO_ROOT/restored-full/docs/report.txt" "$PPT_DEMO_ROOT/restored-full/docs/report-hard.txt"
readlink "$PPT_DEMO_ROOT/restored-full/relative-link.txt"
readlink "$PPT_DEMO_ROOT/restored-full/absolute-link.txt"
ls -l "$PPT_DEMO_ROOT/restored-full/broken-link.txt"
```

`ls -li` 中两个文件应有相同 inode；`diff` 无输出代表内容一致。断开链接是刻意样本，不是恢复故障。普通读文件操作可能更新访问时间，检查时间应在读取内容之前进行。

保留演示的可运行 Java 样例见 `doc/本地功能验收.md` 第 4 节；它读取 `BACKUP_DEMO_DIR`，若本次使用 `PPT_DEMO_ROOT`，先执行 `export BACKUP_DEMO_DIR="$PPT_DEMO_ROOT"`，并将目标设为未使用的 retention 子目录。此时 `keepGroups=1` 只管理此独立演示任务。展示课前结果必须标注为课前记录，不能声称正在现场执行。

时间不足时先缩短功能讲解、跳过错误密码重试和重复格式展示；保留老师/助教亲手完成备份和还原、实际结果核对，以及明确的自动任务停止操作。

### 4.3 常见追问的回答口径

| 问题 | 准确回答 |
| --- | --- |
| 压缩/加密算法自己写的吗？ | 归档组织和备份逻辑自己实现；压缩与密码算法使用 JDK 标准实现，不是自研密码算法。 |
| 为什么两个文件内容相同不一定是硬链接？ | 内容相同不能证明共享文件系统对象，硬链接按文件身份识别。 |
| 为什么备份时不跟随软链接？ | 避免扩大扫描范围和递归循环，保留链接本身的含义。 |
| 为什么恢复成功还有警告？ | 数据已恢复，但部分属性受权限/平台限制；软链接权限回填是主动跳过。 |
| 为什么第 11 次重新全量？ | 限制增量链长度，形成能够整组管理和淘汰的依赖单元。 |
| 为什么重启后不是继续增量？ | 新进程不复用无法确认配置与密码兼容性的旧基线，首次创建全量。 |
| 增量能单独还原吗？ | 通常不能，需先恢复全量及前序增量；界面逐份叠加，不自动串联。 |
| 源目录删除的文件会从还原目录消失吗？ | 不会；当前增量是叠加恢复，不做删除同步。要干净快照应全量恢复到空目录。 |
| 测试覆盖率多少？ | 已有 64 个用例全部通过，但未采集覆盖率，不报百分比。 |
| 支持网盘或多用户吗？ | 不支持。已按项目范围删除网络模块，专注本地备份。 |
